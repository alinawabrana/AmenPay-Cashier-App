## 4. Main Remaining Issue

### Palm Mismatch in New Payment Step 3

Observed issue:
- The current palm scan used during payment produces a different template id on repeated scans of the same palm.
- Because of that, direct backend lookup by `template_id` is not reliable.

Impact:
- Palm enrollment may complete successfully.
- Palm scan during payment may still fail to locate the enrolled customer/payment method because the newly generated template id does not equal the originally stored template id.

Root cause:
- The current SDK/hardware flow does not provide a stable, repeatable identity key that can safely be used as a backend lookup key for the same palm.
- The LNE documentation now provided shows feature extraction output such as:
  - `feature_rgb`
  - `feature_nir`
  - `base_64_rgb`
  - `base_64_nir`
  - `palm_type`
- However, the provided documentation does not show a server-side or SDK-level comparison/search API for matching one scan against previously enrolled palm features.

## 5. Required Solution Direction

The backend lookup should move away from direct `template_id` matching.

Recommended solution:
- Enrollment stage:
  - capture and store palm raw features
  - store `feature_rgb`
  - store `feature_nir`
  - store `palm_type`
  - store optional quality/score values if required
- Payment scan stage:
  - capture fresh palm raw features again
  - compare the fresh features against enrolled palm feature records
  - return a stable matched palm identity or directly return matched payment methods

This means the reliable production solution is:
- feature-based matching, not template-id matching

## 6. Assistance Required from Hardware Company

To complete reliable palm matching, support is required from the hardware vendor.

We need one of the following from them:
- A proper server-side palm matching SDK
- A documented comparison/search API for the raw features returned by the Android SDK
- A complete matching algorithm specification for:
  - `feature_rgb`
  - `feature_nir`
  - `palm_type`
  - similarity calculation
  - decision thresholds
- A supported protocol/service definition for enrollment and recognition using raw palm features
- Sample server-side enrollment and matching requests/responses
- Guidance on whether a stable `palm_id` can be generated from raw feature enrollment and then reused for subsequent scans

Without one of the above, we can capture raw features on device, but we still cannot implement a reliable backend matcher with production confidence.

## 7. Recommended Backend Changes

Backend changes recommended now:
- Stop using palm `template_id` as the final identity key for payment lookup
- Prepare backend models and APIs for feature-based enrollment and lookup
- Add storage for enrolled palm raw features or a stable vendor-supported palm identity
- Change palm payment lookup API to match by enrolled feature identity instead of raw template id

Backend changes not recommended:
- Do not continue building the live payment lookup flow around template-id equality, because current device behavior shows that it is not stable enough.
